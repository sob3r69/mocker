# Файлы и конфликты (этап C)

JSON-файлы в PROJECTS_DIR остаются единственным постоянным источником конфигурации. Runtime-состояние, ревизии и диагностика в них не добавляются. Имя файла должно совпадать с безопасным id проекта: `shop.json` содержит `id: "shop"`.

## Внешние изменения

Chokidar отслеживает каталог без вложенной рекурсии и переходов по symlink. Обрабатываются добавление, изменение, удаление и атомарная замена JSON-файла редактором. События объединяются; незавершённая запись стабилизируется примерно 100 мс перед чтением. Временные файлы не считаются проектами. После подключения watcher выполняется повторное сканирование, чтобы закрыть промежуток между начальной загрузкой и подпиской. Дополнительная сверка раз в две секунды страхует от потерянных системных событий; неизменившиеся файлы не увеличивают версию реестра.

Каждое изменение проходит общую Zod-схему, проверку id/имени файла, prefix и маршрутов. Корректная версия заменяет runtime snapshot целиком. Запрос с уже выбранным ответом заканчивается на прежней версии. Работающий проект продолжает работу; остановленный не запускается автоматически. `enabled: false` останавливает проект. Внешний новый файл загружается остановленным, независимо от autoStart; autoStart применяется только при старте процесса.

При невалидном внешнем изменении известный проект получает `state: "error"`, `error` и, если файл удалось прочитать, `diskRevision`. `revision` и `config` по-прежнему обозначают последнюю корректную конфигурацию. Если проект работал, старые маршруты продолжают отвечать. Его можно остановить, но запуск запрещён до исправления. После исправления восстанавливается прежнее состояние с учётом ручной остановки. Невалидный новый файл виден в диагностике без добавления проекта в runtime.

При удалении JSON-файла проект удаляется из реестра и больше не обслуживает новые запросы. Другие проекты продолжают работу. Если исправление либо удаление другого файла освобождает занятый prefix, конфликтующий файл проверяется повторно.

## Уведомление интерфейса

`GET /api/project-changes` возвращает `{instanceId, version}`. instanceId меняется при перезапуске процесса; version — при изменении конфигурации, состояния или диагностики. Неизменившиеся файлы и собственные события сохранения не увеличивают версию повторно.

React опрашивает этот небольшой endpoint раз в секунду через TanStack Query. При изменении версии инвалидируются серверные query keys `projects` и `project`; локальные черновики редакторов не перезаписываются. В интерфейсе отображается актуальная диагностика; чистый документ обновляется автоматически, dirty draft защищён диалогом конфликта. Очистка опроса выполняется TanStack Query при размонтировании. SSE для журнала запросов относится к этапу F.

## Импорт и экспорт

Импорт принимает полный документ JSON, без multipart и пользовательских путей:

```sh
curl -i -X POST http://127.0.0.1:3001/api/projects/import \
  -H 'Content-Type: application/json' --data-binary @examples/shop.json
curl -f http://127.0.0.1:3001/api/projects/shop/export -o shop-export.json
```

Импорт сохраняет ID и prefix, не заменяет существующий проект и создаёт его остановленным. Неверный JSON/схема — 400, конфликт ID/prefix — 409, превышение MAX_BODY_SIZE — 413. Для намеренной замены существующего проекта применяется PUT config с ревизией.

Экспорт читает актуальный файл, проверяет его и возвращает исходный текст с `Content-Disposition: attachment` и ETag. Он не добавляет runtime-поля. При невалидном файле возвращается 409 CONFIG_INVALID. Поэтому скачивание не выдаёт последнюю рабочую копию за текущее содержимое диска.

## Разрешение конфликта

1. Получить GET `/api/projects/shop`. Его `revision` используется для обычного сохранения через If-Match.
2. При 409 REVISION_CONFLICT получить GET `/api/projects/shop/disk`. Ответ содержит `text`, точную дисковую `revision`, массив `issues` и `config`, если документ корректен. Текст может быть невалидным JSON. Исходный черновик сохраняется в редакторе отдельно до решения пользователя.
3. Для загрузки внешней версии использовать text/config из ответа disk.
4. Для сохранения собственного документа после подтверждения пользователя использовать PUT `/api/projects/shop/config?overwrite=true` с If-Match, равным **проверенной дисковой ревизии**, и валидным JSON body.

```sh
curl -i http://127.0.0.1:3001/api/projects/shop/disk
curl -i -X PUT 'http://127.0.0.1:3001/api/projects/shop/config?overwrite=true' \
  -H 'Content-Type: application/json' -H 'If-Match: REVIEWED_DISK_REVISION' \
  --data-binary @shop-export.json
```

Overwrite не отключает защиту ревизии. Если диск изменился ещё раз после просмотра, сохранение снова вернёт 409. If-Match: * не поддерживается. Без заголовка — 428. Обычные PATCH и изменения endpoints не могут заменить невалидный внешний файл: для восстановления используется полная конфигурация. Для удаления ошибочного проекта можно передать в DELETE актуальную ревизию disk после подтверждения удаления.

## Надёжность и ограничения

Все операции записи и применения внешних конфигураций проходят последовательную очередь. Чтение ограничено MAX_BODY_SIZE даже при росте файла во время чтения. Symlink не читается, где доступен O_NOFOLLOW; API не принимает пути к файлам. Запись использует временный файл в том же каталоге, fsync, повторную проверку ревизии и rename. Создание через link не перезаписывает параллельно появившийся файл. При ошибке временный файл удаляется, runtime не заменяется.

Нужна локальная файловая система с поддержкой hard link и атомарного rename. Атомарность защищает от частично записанного JSON; полноценная межпроцессная транзакция с внешним редактором не реализуется. Между последней проверкой ревизии и rename остаётся короткий промежуток, который обычный filesystem API не позволяет закрыть compare-and-swap операцией. Не запускайте несколько экземпляров приложения с одним PROJECTS_DIR.

При SIGINT/SIGTERM watcher закрывается вместе с обоими listener; ожидаются уже поставленные операции обновления. Автоматические тесты используют временные каталоги и реальные события Chokidar. На macOS в ограниченном sandbox для fs.watch может потребоваться запуск тестов с доступом к системным событиям файловой системы.
